# 迭代一手动测试

## 1. 启动

先准备可用的 OpenAI API 密钥。在项目根目录的 Windows PowerShell 中运行（密钥只放环境变量，不写入仓库或浏览器）：

```powershell
$env:OPENAI_API_KEY = "<你的 API 密钥>"
$env:OPENAI_MODEL = "gpt-5.4-mini"
python -m service.app
```

浏览器打开 <http://127.0.0.1:8765>。页面应显示“模型已配置”及模型名；`GET /api/agent` 只返回模型名、配置状态和工具能力清单，不暴露密钥。默认调用 OpenAI Responses API；需要兼容端点时可设置 `OPENAI_BASE_URL` 为该端点的 `/v1` 根路径，端点须支持 Responses API 函数调用。模型请求在服务端发起，且设置 `store: false`。默认仅监听本机回环地址，不需要安装第三方 Python 包。**未配置密钥时，新任务和追问不可用，历史报告仍可浏览。**

若页面提示“检测到旧版服务进程”，先停止原先运行在 8765 端口的服务，再在已设置 `OPENAI_API_KEY`、`OPENAI_MODEL`、必要时 `OPENAI_BASE_URL` 的同一个 PowerShell 中重新启动。前端会检查 `/api/agent` 公布的可调规则工具能力；旧进程即使读到新版静态页面，也不能执行新版工具。

Windows 服务调用默认 WSL 发行版；可用 `ML1M_WSL_DISTRO` 指定别名。发行版名称可能仍显示 `Ubuntu-22.04`，但系统内部已升级为 Ubuntu 24.04，以 `/etc/os-release` 为准。当前机器的 Hadoop 3.5.0、Java 17 与配置位于 WSL 用户 `awencat` 的 `~/.local` 下，服务会检查并尝试启动 HDFS 与 YARN。首次运行前请核对 `docs/WSL_Hadoop_运行环境.md`，**不要重新格式化 NameNode**。

当前这台机器的 WSL 用户是 `awencat`；交接说明描述的是原运行机器的 `linxinan` 环境。新机器可在 WSL 中执行 `bash /mnt/d/aaaeee/ziliao/大数据/文本2/BigData-lab2/scripts/setup_wsl_runtime.sh`：它会从 Apache 与 Eclipse Adoptium 官方源下载并校验 Hadoop 3.5.0 和 Java 17，在当前用户的 `~/.local` 下复制配置，并且**仅当 NameNode 目录全新且为空时**初始化 HDFS。已有 NameNode 数据绝不可重新格式化。驱动会自动查找这套用户目录运行时。历史报告浏览不依赖运行时；追问不依赖 Hadoop 运行时，但需要模型 API。

如果当前项目在 WSL 中有固定链接，可设置 `ML1M_WSL_PROJECT` 为该链接路径；否则服务将使用当前盘符的 `/mnt/<盘符>/...` 路径。Hadoop 路径、配置和 HDFS 根目录可分别通过 `ML1M_HADOOP_HOME`、`ML1M_HADOOP_CONF_DIR`、`ML1M_HDFS_ROOT` 覆盖。为排查服务启动问题，可设 `ML1M_AUTO_START_HADOOP=0`，此时要求 Hadoop 服务已经运行。

## 2. 先查看已有正式报告

1. 在“已有任务”选择 `20260923T144724Z-3509cc23`。
2. 预期状态“已完成”，五维分数、三表行数、T1/T2、规则和净表版本来自该任务的 `report.json`。例如 Accurate 为 92.66 → 97.19；Complete 为 99.11 → 98.89。
3. 点击“下载本次报告”，核对下载 JSON 的 `task_id` 与页面一致。
4. 页面应显示“历史任务：无大模型决策记录”。该报告早于本次大模型改造，不能拿它证明过去调用过模型。
5. 已配置模型时，“Agent 报告解读”应自动读取报告，说明五维变化、处置和局限，并显示模型名与报告依据。在追问框输入“为什么完整性下降？”，回答应引用本次分数与属性置空；输入“明天票房多少？”，应明确无法从报告确定。
6. 旧任务的 `cleaned.tsv` 不在仓库中时，页面应明确显示净表样例不可用，不能出现编造样例。

“已有任务”下拉只列最近 20 条；更早的历史报告可在“按任务 ID 打开”输入完整 ID 后查看。

这一步只验证已保存的历史报告展示，不证明本机 Hadoop 当前可运行。

## 3. 发起新的端到端任务

1. 使用默认输入：“请使用默认规则清洗 MovieLens 1M，评估清洗前后的五维数据质量，并说明异常处置和局限。”点击“开始清洗与评估”。服务先等待模型选择 `run_hadoop_clean_and_score`；若模型拒绝，不会创建任务。
2. 模型调用成功后页面显示新任务 ID 和“执行中”；`runs/<新任务 ID>.agent.json` 应记录模型名、模型响应 ID、工具名、规则版本、具体参数及规则快照 SHA-256；`runs/<新任务 ID>.rules.json` 是本次作业冻结的规则快照。刷新页面后，在“已有任务”重新选择该任务，仍可看到阶段、参数与模型决策记录。任务期间再次提交应收到并发任务提示。
3. 完成后状态为“已完成”，页面才显示评分。到 `runs/<新任务 ID>/` 检查 `status.json`、`report.json`、`cleaned.tsv`、`clean_process.tsv` 和两份评分 TSV；`runs/<新任务 ID>.service.log` 是服务启动与驱动标准输出日志。
4. 核对报告 `jobs` 含 `score_before`、`clean`、`export_clean`、`score_after` 四个 Job ID；每表 `input = contributing + duplicate + quarantine`；三期数相加等于净表 ratings 行数；本地 `cleaned.tsv` 的 SHA-256 等于报告 `clean_data_sha256`。
5. 页面净表样例应来自新任务的 `cleaned.tsv`；完成后“Agent 报告解读”应自动生成，可追问“隔离了多少条？”和“T1/T2 是什么？”。同一页面会话内重复打开该任务不会重复请求解读。

当前请求框有两个已登记工具：直接运行完整 MovieLens 1M 的 `quality-clean-v1.0.0`，或运行参数受到限制的派生规则。默认提示词仍使用原规则，原始文件和规则版本相同时，清洗计数与五维评分应相同。模型不能把用户明确指定的参数静默忽略。输入“只保留男性用户再清洗”“按 2020 年后的评分清洗”“把评分上限改成 10 再清洗”，均应拒绝且不创建任务。

服务另有保守的请求范围校验，用于阻止模型误选工具或错填参数时静默忽略用户限定条件；如“对女性用户的数据进行清洗并评分”“将年龄门槛定为 25 后评估”也应拒绝。少见的有效表述可能被拒绝，此时使用下列明确表述重新提交。

### 3.1 可调规则手测

以下提示词每次都产生一个独立任务，执行前先核对状态区展示的参数和派生规则版本；完整 Hadoop 作业耗时较长，可以先分别确认模型选择与状态，再选择一组完成端到端运行：

1. **评分门槛：**“清洗 MovieLens 1M，最低保留评分 4。”预期 `min_retained_rating=4`，低于 4 的**合法评分**按 `policy_rating_below_minimum` 计入策略隔离，不能称为无效评分。原始评分合法值仍是 1–5。“把低于 4 分的评分隔离”和“最低保留评分为四分”也应得到相同参数。
2. **标题年份：**“清洗 MovieLens 1M，标题缺少年份时隔离。”预期 `missing_title_year_policy=quarantine`，电影原始行的 `policy_missing_title_year` 与引用已被过滤电影的评分 `policy_filtered_movie_reference` 分开计数；若没有此类评分引用，后一个原因可不出现在报告中。
3. **汇总权重：**“清洗 MovieLens 1M，三表评分权重：评分 5、用户 3、电影 2。”预期 `table_weights={ratings:5, users:3, movies:2}`；Accurate、Complete、Unique、Consistent 的总体分按此权重汇总，Up-to-date 仍只来自评分表。清洗前后必须使用同一权重。
4. **组合：**“清洗 MovieLens 1M，最低保留评分 4，标题缺少年份时隔离；三表评分权重：评分 5、用户 3、电影 2。”三项参数应同时进入规则快照和报告。

以上是受支持的微调范围，不是任意生成新清洗代码。`min_retained_rating=6`、三表权重全为零、未知配置项应在任务创建前失败；用户请求其他筛选条件时也应拒绝。自定义报告应包含 `rule_parameters`、派生的 `rule_version` 和 `rule_sha256`；`quality_before.rule_version`、`quality_after.rule_version` 与 `cleaning.rule_version` 应完全一致。报告中的原始数据版本、净表版本和 T1/T2 仍需核对，以免后续迭代混用产物。

自动解读和追问均会先调用 `read_task_report`，再将所选任务的完整 `report.json` 交给模型。自动解读每次页面会话首次打开一份已完成报告时产生两次模型请求；追问每题也产生两次。追问时请在同一份已完成报告下依次输入下列问题，核对回答确实不同：

1. “评分隔离了多少条？”应只给评分表隔离数 `154,128`。
2. “电影去重了多少条？”应只给电影表去重数 `204`。
3. “无效评分有多少条？”应给原因计数 `43,885`，而不是隔离总数。
4. “为什么完整性下降？”应给 `99.11 → 98.89` 及属性置空原因。
5. “为什么默认规则的结果一样？”应解释相同数据版本与相同规则参数会产生相同评分；派生规则应按自己的版本和参数解释。
6. “明天票房多少？”应明确无法从本次报告回答。

以上数字取自本机完成任务 `20260924T130302Z-f2c0a4e3`；若选择其他报告，应以该报告的实际字段为准。模型回答可能有措辞差异，但不能凭空增加报告没有的事实。

完整任务在交接环境中约需 9 分钟，实际耗时取决于 WSL 和 Hadoop 资源。运行中阶段更新来自 `status.json`，单个 Hadoop 作业内不提供百分比。

## 4. 失败与规则保护

1. 输入“把评分上限改成 10 再清洗”，应在提交时拒绝，说明当前只支持已登记的默认规则及第 3.1 节列出的有限参数调整，不创建任务。
2. 输入与数据治理无关的请求，应说明当前支持的任务范围。
3. 若 WSL、HDFS 或 YARN 不可用，新任务应变为“失败”，显示阶段与原因；报告和评分区不应出现占位结果。查看 `runs/<任务 ID>.service.log` 及 `status.json` 排查。
4. 若原始 `.dat` 被更改或规则登记的原始版本不一致，驱动应拒绝；手测时**不要修改正式原始数据**，可在独立副本中验证这一分支。
5. 同一项目的第二个服务进程尝试提交任务时，应收到任务锁提示。服务意外终止后，先核查 YARN 和 `runs/<任务 ID>/status.json`，确认旧任务已停止，再处理 `runs/.active-task` 锁目录。
6. 另开一个未设置 `OPENAI_API_KEY` 的 PowerShell，在未占用的端口启动服务：`python -m service.app --port 8766`。页面应显示未配置；新任务和追问不可用，旧报告可浏览。模型服务返回错误或超时时，不应回退为关键词模板答案，也不应启动 Hadoop。

## 5. 自动测试

```powershell
python -m unittest discover -s tests -v
```

自动测试覆盖既有清洗规则语义、原始文件哈希、Responses API HTTP 请求、模型工具选择、报告工具回传、缺少密钥与错误路径、历史报告读取及 HTTP 接口。模拟模型不代表真实云端验收；仍需按第 3 节使用有效 API 密钥和 Hadoop 实测。
