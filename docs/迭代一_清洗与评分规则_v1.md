# 迭代一清洗与五维评分规则 v1.0.0

对应机器可读配置：`config/quality_rules_v1.json`。原始输入版本见 `raw_data_manifest.json`。本规则在清洗作业运行前固定；如因实现错误或新证据需要修改，另起版本，并对修改原因和前后结果重新计算。

Agent 的默认工具仍原样执行本规则。用户明确提出微调时，服务仅允许更改最低保留评分（1–5）、标题缺少年份的处置（保留标记或隔离）和三表总体评分权重（各为非负整数，至少一个正数）。每个任务保存完整规则快照；不同于默认值的组合以参数与执行代码哈希形成派生 `rule_version`，Hadoop 的清洗前评分、清洗和清洗后评分共用它。低于最低保留评分的合法记录是用户指定的**策略过滤**，在报告中以 `policy_rating_below_minimum` 单独计数，不算作原始数据无效；同一评分事件的冲突仍先按原规则判断，不能靠过滤低分把剩余高分当作可信真值。严格隔离缺少年份的电影也会单独计数，引用仅被过滤电影的评分记为 `policy_filtered_movie_reference`。原始数据始终不变。

## 1. 输入和输出约定

- 原始三个 `.dat` 文件只读，按 ISO-8859-1 解码、`::` 分割，不把首行当表头。原始文件的 SHA-256 必须与清单一致，否则任务失败。
- Hadoop 任务保留来源文件及字节偏移或等价的稳定来源标识。所有计数、异常样例和分数来自本次实际运行结果，不写死在界面或报告中。
- 清洗输出使用 UTF-8 的带表名 JSONL，`fields` 数组保持原有字段顺序；不确定的可选属性写为 `\N`，邮编始终按字符串保存。评分器将 `\N` 视为缺失。原始输入仍按 `::` 解析。
- 每条原始行只进入一种最终去向：贡献到保留结果、去重移除、隔离。用户和电影的多条非重复原始行可能合并为一条输出，因此另计“参与合并的来源行数”和“输出记录数”。字段规范化和冲突置空也须另行计数，不能把隔离或置空称为已修复真实性。
- 对每张表输出输入行数、贡献行数、去重行数、隔离行数、输出记录数以及处理原因。原始行数须等于前三种去向之和；额外保留隔离明细与少量可展示样例。

## 2. 清洗规则

| 情况 | 处理 | 理由与记录方式 |
| --- | --- | --- |
| 字段数不符合表结构、关键 ID 缺失或无法解析 | 隔离该行 | `::` 无转义规范，不能可靠猜测字段边界；记录原文与原因。 |
| 字段两端多余空白、数值字段前导零 | 确定性规范化 | 规范化前后值都入审计；邮编不做数值转换。 |
| 评分不是 1–5 的整数，或时间戳不是规定历史范围内的 Unix 秒 | 隔离该评分 | 不把小数强制取整，也不猜测毫秒和秒的换算。 |
| 完全相同的评分业务事件重复 | 无冲突时保留一条，其余去重 | 业务事件键为 `(UserID, MovieID, Timestamp, Rating)`；同一用户在不同时间评分允许保留。 |
| 相同 `(UserID, MovieID, Timestamp)` 对应多个不同评分 | 隔离冲突事件的全部候选行 | 无法从数据本身判断哪一分是真值。 |
| 评分引用不存在的用户 ID 或电影 ID | 隔离评分 | 不创建虚构用户或电影。 |
| 用户的性别、年龄、职业取值无效，或用户属性同 ID 冲突 | 保留可识别的用户 ID；仅把不确定属性置为 `\N` | 不因此丢弃该用户的有效评分；报告属性缺失和冲突。 |
| 同一电影 ID 的标题或类型互相冲突 | 保留可识别的电影 ID；逐字段把不确定属性置为 `\N` | 不通过多数表决猜测电影信息；报告受影响电影和评分规模。 |
| 类型中包含未知名称 | 移除未知类型标记并留审计；若无已知类型则记为 `\N` | 保留可确认的类型，不擅自映射未知名称。 |
| 邮编不符合常见美国邮编形式、标题年份缺失或疑似乱码 | 保留并标记 | 邮编可能有其他合理形式；标题和年份无法仅凭格式证明真实或错误。 |

对 `users` 和 `movies`，同一 ID 的完全相同记录只保留一条；若属性冲突，先规范化再按字段合并：一个字段只有一个确定有效值时保留，有两个及以上不同有效值时置为 `\N` 并记录冲突。空值不会投票覆盖确定值。若 ID 本身无法解析，该行隔离。

先按 `(UserID, MovieID, Timestamp)` 判断评分冲突：有不同评分时，整组候选行隔离，不再计入去重；无冲突时才去除完全重复事件。所有跨表检查使用同一次任务生成的用户和电影 ID 集合。评分事件去重、冲突判断和跨表检查必须在结果落盘前完成。

## 3. 五维评分口径

评分器对清洗前后运行同一个规则版本。每项保留分子、分母和逐表得分，展示时才四舍五入到小数点后两位。空表记为“无法评价”，不写成 0 分。

对 Accurate、Complete、Unique、Consistent，先分别计算三张表的百分制得分，再对非空表等权平均，防止百万条评分掩盖用户或电影表的问题。Up-to-date 只评价有事件时间的评分表，不假装用户和电影属性有更新时间。本轮不设置综合分。

若用户明确配置三表权重，则前四个维度从等权平均改为对非空且权重大于零的表做加权平均，清洗前后均使用同一组权重。Up-to-date 不受三表权重影响。不同权重版本的总体分不能直接作为同一口径的前后对比。

| 维度 | 可执行定义 | 解释边界 |
| --- | --- | --- |
| Accurate | 每张表中“全部期望字段存在，且可检查值符合已登记取值域”的行数 ÷ 该表输入行数 × 100。评分检查正整数 ID、1–5 整数评分和有效历史秒时间戳；用户检查类别代码；电影检查正整数 ID、非空标题和已知类型。 | 这是**可验证值合法性代理分**；无法证明用户填写资料、电影标题或评分反映真实世界。 |
| Complete | 每张表期望字段中非空且非 `\N` 的槽位数 ÷（该表行数 × 期望字段数）× 100。字段数不足视缺少槽位，多出字段不增加分子。 | 只衡量登记的字段是否可用，不能判断缺失信息能否从外部恢复。 |
| Unique | 每张表不重复的完整业务行数 ÷ 该表行数 × 100。比较前对可解析字段使用本规则的确定性规范化；无法解析的行按原文比较。 | 不把同一用户对同一电影在不同时间的评分算作重复；同键异值由 Consistent 反映。 |
| Up-to-date | 评分表中，时间戳落在 2002-03-01 00:00:00 至 2003-02-28 23:59:59 UTC 的行数 ÷ 评分表总行数 × 100。 | 以数据集发布时期为固定参照，衡量当时近一年的行为占比。合法的旧评分仍然有研究价值，低分不等于应删除；缺乏真实入库时间，不能评价处理延迟。 |
| Consistent | 每张表中同时满足字段数正确、数值文本格式统一、同 ID 或同事件无矛盾的行数 ÷ 该表行数 × 100；评分还需引用存在的用户和电影 ID。默认三表等权，派生规则可按登记权重汇总。 | 只能检查数据内部矛盾及跨表关系，不能证明外部事实一致。 |

对 Unique，“完整业务行”在评分表为四字段元组，在用户和电影表为各自整行字段元组。相同 ID 的冲突属性不会被当作普通重复。对 Consistent，数值文本格式统一指正整数或允许的非负类别编码采用无符号十进制写法，时间戳单位为秒；邮编不受此规则约束。

清洗后只对**保留的数据集合**重新评分。报告必须同时展示保留率、去重率、隔离率、属性置空数和各分数的分母；评分提高可能来自隔离问题记录，不能单独解读为原始问题已被修复。

## 4. 时间边界和后续使用

清洗成功后，仅用保留评分的时间戳按 UTC 日期统计累计数量。`T1` 取累计量首次达到 80% 的日期 23:59:59 UTC，`T2` 取首次达到 90% 的日期 23:59:59 UTC；同一天的评分不跨期。训练期为 `timestamp ≤ T1`，验证期为 `T1 < timestamp ≤ T2`，测试期为 `timestamp > T2`。如果任一期为空，任务标记失败并要求人工修订切分方案及规则版本。

时间边界连同原始数据版本、清洗规则版本和本次清洗数据版本写入结果清单。第二轮的用户历史画像、特征和模型训练只读取 `T1` 及以前数据；验证与测试数据只用于相应评估。

## 5. 预分析与限制

目前的只读预分析发现原始评分存在约 9.2 万条完全重复行，三个文件均有字段数错误，用户和电影 ID 存在属性冲突。这些数字仅用于制定规则，**不是 Hadoop 清洗结果或正式五维评分**。正式报告以 Hadoop 任务输出及对账结果为准。

MovieLens README 说明用户属性未经核实，电影条目可能有人为录入错误。因此真实准确性和文本乱码的自动修复能力有限；本规则保留这些限制，并在报告中单独展示未解决问题。
